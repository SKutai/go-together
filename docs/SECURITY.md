# Security

To report a vulnerability, see
[Reporting a vulnerability](#reporting-a-vulnerability) below.

Go Together is a local game, not a security boundary. It has no accounts,
server-side API, analytics, or application-initiated third-party network calls.
The browser build fetches its JavaScript, WebAssembly, and assets from the same
origin. Trunk's development server can inject a local autoreload WebSocket
while serving; `Trunk.toml` turns that off (`no_autoreload = true`), and it is
not part of a release build in any case.

## Trust boundaries

- **Native local data is untrusted input.** Settings and Replay JSON may be
  edited, truncated, replaced, or generated by another program with access to
  the user's account. Loaders must validate schema versions, value ranges,
  collection sizes, identifiers, filenames, and Replay relationships before
  using them. This includes Settings/Replay v5 integer-second bounds, immutable
  rule snapshots, timeout causes/deadlines/submissions, capture totals and
  per-round deltas, and canonical end-reason lists. A corrupt item should not
  hide unrelated valid items.
- **Browser local data is also untrusted.** Settings and completed Replays use
  same-origin browser storage. Any script running on that origin can read or
  change those values, so they must not contain secrets and must be validated on
  every load. Storage quota, user clearing, private-browsing policy, or an
  embedding host can make persistence unavailable.
- **A headless consumer of the library meets the same gate.** Outside this
  crate a `go_together::replay::Replay` can be obtained only through
  `Replay::from_json` (size-bounded to `MAX_REPLAY_JSON_BYTES`, then parsed,
  then fully validated) or `Replay::from_value` (parsed, then fully
  validated); the type has private fields and deliberately no
  `serde::Deserialize` impl, so no consumer can hold a Replay that skipped
  `Replay::validate`. Serializing back out (`to_storage_json`) trusts what it
  is given, as the game's own write path does - see `Replay::validate`'s doc
  comment for the ownership policy.
- **The distribution is trusted code and content.** JavaScript, WebAssembly,
  executables, and bundled `assets/` execute or influence the game. Obtain them
  from the repository or a future documented release channel and verify future
  signatures/checksums where available.
- **Input devices and UI events are not authenticated.** Keyboard and gamepad
  events are appropriate for a local game, not for proving player identity or
  protecting competitive results.
- **Diagnostics shown to a player are deliberately generic.**
  [`crate::diagnostics::report_recoverable`](../src/diagnostics.rs) logs
  full technical detail (which may include a local file path or a raw OS
  error) but only pushes a concise, safe message onto the shared
  `Diagnostics` log. That holds for every push without exception - no
  `Diagnostic` in the crate carries a filesystem path - and a test pins the
  exact message at each site that makes one. Not every per-screen
  error display holds to that standard: the Replay rename/delete dialogs and
  the Settings screen's startup load warning deliberately show the detailed
  message, on the reasoning that a cause named in response to the player's
  own attempt is actionable on a local desktop game. The load warning shows
  as much of it as its line on screen holds and is cut beyond that, so a
  long path or cause reaches the log whole but the screen only in part.
  That reasoning is local to a single-process game, so a future networked
  host must not assume every on-screen error string is already safe to relay
  to a remote peer; it would need its own review at that point.

The web shell uses a restrictive Content Security Policy as defense in depth and
has no service worker. Same-origin hosting still controls the page, and CSP does
not make hostile hosting safe. Browser storage is deliberately conservative:
only a bounded settings/catalog representation and exactly the newest three
completed Replays are retained. Records the application cannot read are the
one thing it neither uses nor deletes - it keeps and reports them, because a
record that fails to deserialize may have been written by a newer version of
the application rather than corrupted; see `docs/ARCHITECTURE.md`'s platform
adapter boundary.

## Match state privacy and a future network boundary

Go Together runs as one local, shared-screen process today: there is no
network, no remote client, and no untrusted player input in the sense a
server-authoritative game needs to defend against. The following boundary is
established for a possible future online mode and is enforced today only at
the type level and by this crate's own tests, not by any running server:

- **`go_together::authority::MatchState` is the trusted host's complete
  state**, including both players' hidden Round 0 selections and pending
  ordinary lock - something the authoritative side of a Match must hold to
  resolve a round at all. It is never a client-safe payload: nothing serializes
  it wholesale and sends it to "a player," and a future server must not either.
- **`go_together::view::PublicMatchView` and `PlayerMatchView`** are the
  read-only, privacy-scoped projections a future networked opponent,
  spectator, broadcast, or remote client-side UI should actually receive.
  They contain no field the wrong player's hidden data could occupy - not
  "the recipient happens not to render this field," but "this type has no
  such field" - so no rendering choice can show a player the opponent's data
  itself. One inference channel survives that structure and carries its own
  rule: `PlayerMatchView::own_selected_point` is the owner's *own* pending
  selection, legitimately present, and after a press on a visibly empty
  point, whether it is `Some` is the accepted-or-reserved answer that
  silent rejection refuses to give - so surfacing it while its round is
  unresolved would read out the opponent's hidden point by its absence. A
  future server therefore withholds or blanks that one field in anything it
  sends mid-round; the field's own documentation carries the full
  reasoning. The structural guarantee above concerns the opponent's data,
  while this is a timing rule on the owner's.
  Nothing receives them today, and the local shared-screen UI is
  deliberately not such a consumer: it is the trusted host's own renderer for
  two players at one monitor and reads `MatchState` directly by design, so
  its own obligation is a rendering discipline (never draw either player's
  hidden data during live play), not this type boundary. What that
  discipline does not cover is a *resolved* selection: once a round has
  resolved, where each player played is no longer hidden - the Replay
  records it and the board shows its result - so the public view's
  `last_removals`, which can name a stone that was placed and removed within
  one round and so stood on no displayed board, publishes nothing the rules
  still keep secret. The Round 0 dot rows, and the
  `last_opening_attempts` record the public view publishes for them, are
  the one place that discipline was argued rather than assumed, because the
  opening is still secret while they show it. Per player they carry how
  many points are held, what the last selection did - added a point,
  rolled the window forward, or was a duplicate - and how many selections
  have been made; never a point, and never which held point a duplicate
  repeated, since a duplicate always strikes the newest dot and a
  roll-forward always drops the oldest, which the rules always remove. The
  count was already on screen, so every addition below three was already
  public with its moment, and every duplicate was already public through
  the clack, which both players hear. What is new is a selection accepted
  with three held: before 2026-10-03 it changed no count and played no
  sound, so the screen never showed that it had happened. (The clack's
  absence could be read as already saying so, but only by an opponent who
  saw the press itself - usually so at one keyboard, but never something
  the game showed.) It is still safe to
  show, because it says that and when a player changed their mind and
  nothing about where: Round 0 cursors and every cursor move are hidden,
  so the new point could be any point the player did not already hold,
  and the point it displaced is fixed by order, not choice. Nothing in it
  gives an opponent a point to aim for or avoid. With motion reduced, a
  roll-forward that follows an accepted selection changes nothing on
  screen at all, so the static form shows strictly less than the
  animation. Because these types
  have no caller to exercise them, `src/view.rs` holds itself to the
  contract: both constructors destructure `MatchState` and `MatchProgress`
  exhaustively, so a newly added authoritative field cannot silently go
  unclassified, and its tests assert every projected field against its
  authoritative source. See `crate::view`'s module docs for exactly what each
  audience may see and why, and `docs/ARCHITECTURE.md`'s "Match state privacy
  and trust boundaries" for what those two guards do and do not catch.
- **`go_together::replay::Replay`/`ReplayFrame` are complete historical
  records for authorized after-the-fact viewing**, deliberately including
  both players' Teleport Markers and resolved selections once a Match has
  concluded (or from any Replay frame after the fact). A Replay must never be
  reused as a live network sync format or a live client view: it discloses
  information a live opponent is never shown during play, and it is not
  designed to be sent incrementally or to represent "what one player may see
  right now."
- **A future untrusted client's commands would need a trust split this crate
  does not implement yet.** Every command method on `MatchState` that needs a
  player identity or a Match-clock time already takes it as a caller-supplied
  parameter (`try_lock(player, now)`, `move_cursor(player, ..)`,
  `advance_clock(budget)`) rather than reading it from stored or untrusted
  state; a future networked host would keep that shape while stopping short of
  trusting the network for either one. A remote client should submit only an
  *intention* (which action, which point) and never be trusted to also choose
  its player identity, assign its own authoritative timestamp, replace
  arbitrary `MatchState`, or claim a move already succeeded - the host
  attaches identity and time before calling the same command methods
  `gameplay` calls today. No networking, authentication, or distinct
  intent/command protocol types exist yet; this describes the intended shape
  without introducing unused scaffolding ahead of an actual transport.
- **A Match preset is a proposal, not an authoritative input.** `MatchSettings`
  (Round Limit, Round Time, Match Time, Point Target, the no-board-change
  round limit, Capture Points) is a local client's *preferred* rules for its
  next Match - see `docs/ARCHITECTURE.md`'s "Configuration ownership"
  section. A future networked host must not accept a preset value verbatim
  from a client as the Match's actual rules: it should treat it as a
  negotiable suggestion (for a host migrating rules, or players agreeing on
  one before a Match starts) and attach the *agreed*, validated snapshot
  itself - the same
  `authority::MatchRules::snapshot` construction used today - as part of
  starting the authoritative Match, exactly as it must already do for player
  identity and timestamps in the point above. Local client settings -
  keyboard bindings, controller profiles, audio and display preferences -
  are a stricter case still: they describe only how a physical device maps
  to a semantic action or how this one screen renders, never something a
  remote peer could need or should be able to influence, and must never
  become part of any future authoritative Match protocol at all.

## Dependencies and automation

Rust dependencies are resolved through `Cargo.lock` for reproducible application
builds. CI uses least-privilege `contents: read`; every GitHub Action reference
is pinned to a full commit SHA with a human-readable version comment. Dependabot
checks those GitHub Actions pins weekly. Review action and dependency updates as
code changes rather than merging them solely because a bot opened them.

Trunk is fixed at version 0.21.14 in configuration and CI. Release maintainers
should record tool versions and review the resulting dependency changes before
publishing. The checked-in build does not enable an automatically downloaded
WebAssembly optimizer; adding a native build tool requires an immutable source
and verified checksum.

**Rust dependency updates are not automated.** Dependabot's only configured
ecosystem is `github-actions` (`.github/dependabot.yml`); crates.io
dependency version bumps must be proposed manually. `cargo tree --duplicates`
is a useful manual check for divergent transitive versions before adopting a
new dependency. Every duplicate in `Cargo.lock` today is transitive, mostly
Bevy-graph and platform-specific noise; none of this project's own direct
dependencies appears there at two versions. No license-policy tool
(`cargo-deny` or similar) is configured; this project's own license is MIT
and its direct dependencies are drawn from the ordinary, permissively
licensed Rust/Bevy ecosystem, but no automated check enforces that today.

`cargo audit` runs from `.github/workflows/audit.yml` (installed via
`cargo install cargo-audit --locked --version 0.22.2`, cached on that pinned
version the way Trunk is in `ci.yml`'s `web` job), scanning `Cargo.lock`
against the RustSec advisory database. The scan and the install that precedes
it are both `continue-on-error: true`, so neither can turn a run red: a newly
published advisory in a transitive dependency with no available fix yet is not
a statement about this repository's code. The advisory set moves with the
RustSec database and `Cargo.lock` independently of this repository, so that
workflow's log is the live answer and a maintainer can run `cargo audit`
locally at any time for the current, authoritative result.

It runs **weekly, and on manual dispatch** - never on a push or a pull
request. Nothing gates on it, so running it per commit would spend a third
runner on every push to produce a log nobody is required to read, and the
advisory database moves on its own timeline rather than with this repository's
commits. A weekly answer is as current as a per-push one in every way that
matters, and the Actions tab's *Run workflow* button is there for when it is
not.

It also runs on a runner of its own. `cargo install cargo-audit` compiles
`rustls` and `aws-lc-rs` in release mode, and as the last step of `native`, on
a runner that had already built Bevy with full debug information, built
documentation and run the whole test suite, that exhausted the disk in
September 2026. The install is guarded as well as the scan because a guard on
the scan alone is never reached when the install fails first, and the check
meant to be informational is then what fails the run. A fresh runner removes
the disk pressure rather than masking it. `native` no longer builds debug
information, and the room it saves is margin for its own growth, not space
for an unrelated tool; see
[CONTRIBUTING.md](../CONTRIBUTING.md#required-checks). The job also sets
`RUSTFLAGS` empty: `-D warnings` is a rule about this repository's own code
and has no business denying warnings in a third-party tool's dependency tree.

The one finding recorded when this scan was added was an informational
"unmaintained" warning (not a vulnerability) for
`ttf-parser`, a transitive dependency of Bevy's text-rendering stack
(`RUSTSEC-2026-0192`) - outside this project's control to fix directly, since
it would require an upstream Bevy dependency change, and noted here rather
than suppressed.

## Reporting a vulnerability

Report a suspected vulnerability privately, through GitHub's private
vulnerability reporting: open the repository's
[Security tab](https://github.com/SKutai/go-together/security), which GitHub
currently labels "Security and quality", and choose **Report a
vulnerability**. You need to be signed in to GitHub. The report is visible
only to you and the repository's maintainers unless and until it is
published as an advisory, so it may hold whatever shows the problem.

If that button is not there once you are signed in, private reporting is
switched off. Open an [issue](https://github.com/SKutai/go-together/issues)
saying only that you have a security report to make, with no details, and
wait to be given a private way to send it.

What belongs in a private report is anything that could harm a player who has
done nothing unusual: a crafted Settings or Replay file that does anything
worse than being rejected when it is loaded, a flaw in the web shell or its
Content Security Policy, a dependency or workflow that could put something
unintended into a build. Say which build you tested - a commit, or the name
of a download - the platform, the impact, and the smallest reproduction you
have.

Everything else is an ordinary bug and goes in a public
[issue](https://github.com/SKutai/go-together/issues/new/choose), where a
form asks for what a fix needs. That includes a rule that resolves wrongly, a
crash in ordinary play, and anything the trust boundaries above already
describe as outside what a local game defends against. If you cannot tell
which kind you have, report it privately. Because issues are public, do not
attach credentials or other sensitive material there; describe such material
rather than posting it.

## Distribution status

The project does not currently publish release artifacts. No binaries or web
archives are currently signed, notarized, uploaded, or covered by published
checksums. See [DISTRIBUTION.md](DISTRIBUTION.md) for the future release process.
Do not infer authenticity from a filename alone.

A release build is made so that it carries no path of the machine that built
it - a compiled program otherwise holds its builder's home folder, and so
their user name, in the source locations a panic reports - and the scripts
that make it check it for one. What is published is checked again, archives
included, for such a path and for the builder's user name, which an archive
can carry as the owner of its files. See
[Paths of the build machine](DISTRIBUTION.md#paths-of-the-build-machine).
